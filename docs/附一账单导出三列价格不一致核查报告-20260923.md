# 附一账单导出「单价（把）/单价/总价」三列价格不一致核查报告

**日期：** 2026-09-23  
**核查对象：** 黑龙江中医药大学附属第一医院（ZYY-D1）11 列账单导出  
**问题级别：** P0（导出金额自相矛盾，财务不可直接采信）  
**范围说明：** 本报告聚焦**账单导出三列价格写入逻辑**与**行数据落库一致性**，不展开附一计价规则本身是否应 8 折/九九折等业务争议。

---

## 1. 问题现象

用户提供的导出样例（账期约 2026-08，类型为「额外外包（纸塑袋）」）中，同一明细行出现：

| 包名 | 包数 | 把数 | 单价（把）L 列 | 单价 M 列 | 总价 N 列 | 算术关系 |
|------|------|------|----------------|-----------|-----------|----------|
| 妇科刮勺-1/z7537 | 1 | 1 | **6.40** | **8.00** | **8.00** | M=N，但 L≠M |
| 卵圆钳-1/Z1535 | 1 | 1 | **8.80** | **11.00** | **11.00** | 同上 |
| 上取环包 | 1 | 11 | **5.50** | **60.50** | **60.50** | 5.50×11=60.50 ✓ |

**核心矛盾：** 单把器械行（把数=1）时，「单价（把）」已是折后/校正口径，而「单价」「总价」仍显示更高的包级原价；多把行反而自洽。

数值特征：

- 6.40 ÷ 8.00 = **0.80**
- 8.80 ÷ 11.00 = **0.80**

与附一当前 `billingPolicies` 中第一步「八折」高度吻合，说明**折扣已在某一列生效，但未同步到另外两列**。

## 2. 附一 11 列语义（业务约定）

依据 `docs/账单导出客户确认包/01-账单导出规则说明.md` 与院方需求登记：

| 列 | 含义 |
|----|------|
| 单价（把） | 单把器械单价 |
| 单价 | 单包单价（整包计价口径） |
| 总价 | 行合计（通常 = 单价 × 包数；附一常见包数=1） |

**当把数=1、包数=1 时，三列应满足：**

```text
单价（把） = 单价 = 总价
```

**当把数>1 时：**

```text
单价（把） = 单价 ÷ 把数   （或等价：单价 = 单价（把） × 把数）
总价 = 单价 × 包数
```

样例第 3 行（11 把）符合上述关系；前两行违反「单把时三列相等」的不变量。

## 3. 技术根因（代码链路）

### 3.1 导出写列入口

账单 Excel 写出时，三列分别调用 `BillExportPriceResolver` 的三个方法（`HospitalReconciliationServiceImpl.writeSheetFromTemplate` / 模板回填逻辑）：

```text
L 列 单价（把）  ← resolvePerPiecePrice(row)
M 列 单价       ← resolveUnitPrice(row)
N 列 总价       ← resolveTotalPrice(row)
```

三列**不是同一数据源**，而是三套解析策略。

### 3.2 根因 A：`resolvePerPiecePrice` 对单把行优先「冻结」导入单价

`BillExportPriceResolver.resolvePerPiecePrice`（BillRowItem 分支）逻辑摘要：

1. 若把数 **> 1**：由「总价 ÷ 包数 ÷ 每包把数」反推把价（与 M/N 同源，故多把行一致）。
2. 若把数 **= 1**：**优先**读取 `row.original.importUnitPrice`，若存在则直接返回，**不再与 M/N 对齐**。

`importUnitPrice` 的来源（export-v2 路径）：

```java
// BillExportRequestMapper.toBillRowItem
if (row.getUnitPrice() != null) {
    item.setOriginal(Map.of("importUnitPrice", row.getUnitPrice())); // 取 DB 的 unit_price
}
// 随后又把 item.unitPrice 覆写为 resolveUnitPrice(entity) 的结果
```

即：**L 列锚定 DB 里的 `unit_price` 快照；M/N 列锚定解析后的导出单价/总价。**

单测 `BillExportPriceResolverTest.prefersImportUnitPriceForPerPieceColumn` **明确允许** L≠M（import 22.4 vs expected 30.4）。该设计初衷是「保留原始导入把价」，但在附一折后口径下会变成**同一行两个单价并存**。

相关文件：

- `backend/src/main/java/com/hospital/backend/export/BillExportPriceResolver.java`（约 44–62、118–127 行）
- `backend/src/main/java/com/hospital/backend/export/BillExportRequestMapper.java`（约 46–57 行）
- `backend/src/test/java/com/hospital/backend/export/BillExportPriceResolverTest.java`（`prefersImportUnitPriceForPerPieceColumn`、`entityRowPerPieceUsesOriginalUnitPrice`）

### 3.3 根因 B：`resolveExportTotal` 在「单价已对齐、总价未回写」时不再重算

M/N 列依赖 `resolveExportTotal`，其关键分支（简化）：

```text
recomputed = expectedUnitPrice × packCount
若 correctedTotalPrice 仍等于原始 totalPrice（未重算）
   且 unitPrice 与 expectedUnitPrice 已相等（unitChanged = false）
→ 返回 correctedTotalPrice（原价总价），而非 recomputed
```

触发用户所见 **6.40 / 8.00** 的典型 DB 行状态：

| 字段 | 值 | 说明 |
|------|-----|------|
| `unit_price` | 6.40 | 已写入折后把价/单价 |
| `expected_unit_price` | 6.40 | 与 unit 一致 |
| `total_price` | 8.00 | 导入原价 |
| `corrected_total_price` | 8.00 | **未随折后单价回写，仍等于原价** |

此时：

- `resolvePerPiecePrice` → 读 `importUnitPrice`=6.40 → **L=6.40**
- `resolveExportTotal` → `unitChanged=false` → 返回 8.00 → **M=N=8.00**

相关文件：

- `BillExportPriceResolver.resolveExportTotal`（约 145–171 行）
- 注释已提及「附一 7 月 P0」场景，但 guard 条件在「unit 与 expected 已同步、corrected 未同步」时仍会失效

### 3.4 根因 C：导入阶段未区分「单价（把）」与「单价」

`ExcelBillImportSupport` 仅读取表头 **「单价」** 写入 `unitPrice`，**不读取「单价（把）」列**：

```java
Object unitPriceRaw = getCellByHeader(row, headerMap, "单价");
rowData.put("unitPrice", toDoubleOrNull(unitPriceRaw));
```

11 列布局下 Excel 同时存在 L「单价（把）」与 M「单价」，落库却只有单一 `unit_price` 字段。后续导出再「拆回」两列时只能靠引擎字段 + `importUnitPrice` 快照拼凑，**数据模型先天不足**。

相关文件：

- `backend/src/main/java/com/hospital/backend/service/impl/ExcelBillImportSupport.java`（约 94–123 行）

### 3.5 导出路径差异（加重排查难度）

| 路径 | 行数据来源 | 是否设置 `original.importUnitPrice` | 单把行 L 列行为 |
|------|------------|-------------------------------------|-----------------|
| export-v2（`ExportEngineServiceImpl` → `BillExportRequestMapper.fromContext`） | DB 实体映射 | **是**（DB `unit_price`） | 易与 M/N 分裂 |
| export-template-bill（`loadBillRowsFromDb`） | DB 直读 + resolver 覆写 | **否** | L 列多回落到与 M 相同 |

两条路径对同一 Job 可能表现不同，增加「有时正常、有时分裂」的错觉。

## 4. 与用户样例的数值对照

### 4.1 单把行（问题行）

以「妇科刮勺」为例，在附一高温纸塑 **单件按袋规计费** 规则下，标准包价常为 **8.00** 元；叠加 bill_detail 八折后 **6.40** 元。

| 阶段 | 单价（把）口径 | 单价/总价口径 |
|------|----------------|---------------|
| 计价引擎折后 | 6.40 | 应为 6.40 |
| 导出实际写出 | 6.40（L） | 8.00（M/N） |

说明：**折后价写进了 L 列锚点（或 DB unit_price），M/N 仍走未折的包价总价。**

### 4.2 多把行（正常行）

「上取环包」把数 11：resolver 对把数>1 **强制由总价反推把价**，L/M/N 共用 `resolveTotalPrice` 结果，故 5.50×11=60.50 自洽。

这反向证明：**缺陷集中在把数=1 且存在 importUnitPrice 快照 / correctedTotal 滞后的分支**，而非 Excel 模板或 POI 写单元格错误。

## 5. 是否为共性问题？

### 5.1 影响面分级

| 维度 | 结论 |
|------|------|
| **医院范围** | **附一专属高发**。仅 ZYY-D1 使用 `fuyi_extended_11col` 布局，单独暴露「单价（把）」列。 |
| **标准 8 列医院** | **低**。无 L 列，用户只见单价/总价，不会出现「三列交叉矛盾」的同一视觉模式。 |
| **行型** | **单把行（instrumentCount=1）高发**；多把行因反推逻辑通常一致。 |
| **数据状态** | **`unit_price` 与 `expected_unit_price` 已折后，但 `corrected_total_price` 仍等于导入 `total_price`** 时必现。 |
| **规则变更/重算** | 附一 2026-09-23 起 bill_detail 叠折（0.8×0.99）后，若 Job **未全量重算落库**，历史行更易踩中「单价已变、总价未变」。 |
| **export_only 折扣院** | 太平/呼兰等走 `ExportStageDiscountApplier` 的院，理论上也可能出现「导出覆写单价但未同步 original 快照」，但无第三列把价，**外部表现较轻**。 |

### 5.2 结论

- **不是**全平台 37 院账单导出普遍错误。  
- **是**附一 11 列布局下的**结构性缺陷**（单列落库 + 三列双源解析 + 总价回写 guard 漏洞）。  
- 在「规则升级后未重算 Job」「手工改单价未改总价」「export-v2 + 单把行」组合下**可稳定复现**。

## 6. 与计价规则问题的边界

用户要求暂不谈「附一计价规则对不对」，本报告区分两层：

| 层级 | 内容 | 本报告是否覆盖 |
|------|------|----------------|
| 规则层 | 8 元是否应变 6.4、是否叠 0.99、产品规则封存等 | **否**（另案：ZYY-D1 billingPolicies / productRules） |
| 导出层 | 同一行三列是否自洽、是否与 DB 校正字段一致 | **是**（当前缺陷） |

即使规则层完全正确，只要 DB 行处于「折后 unit + 原价 corrected_total」或「L 列冻结 import、M/N 走另一解析」，导出仍会**在 Excel 上呈现自相矛盾**，属于独立 P0。

## 8. 修复方向建议（供审阅，本次未改代码）

### 8.1 短期（导出层，低风险）

1. **单把不变量：** `instrumentCount<=1` 时，`resolvePerPiecePrice` 应返回与 `resolveUnitPrice` 相同值，**禁止**单独冻结 `importUnitPrice`（除非显式「展示原价把价」开关）。
2. **强化 `resolveExportTotal`：** 当 `|correctedTotalPrice - expectedUnitPrice×packCount| > ε` 时，一律以 `expectedUnitPrice×packCount` 为准，**移除**对 `unitChanged` 的依赖。
3. **统一导出路径：** `loadBillRowsFromDb` 与 `BillExportRequestMapper` 对 `original.importUnitPrice` 的处理对齐，避免 v1/v2 行为分叉。

### 8.2 中期（数据层）

1. 导入时分别落库 `import_per_piece_price` 与 `import_pack_unit_price`（或 JSON 扩展字段），不要用一个 `unit_price` 扛两列语义。
2. Job 规则版本变更（如附一叠折上线）后，提供**批量重算 corrected_total** 的迁移脚本/管理接口，消除历史脏数据。

### 8.3 验收门禁

1. 新增单测：`instrumentCount=1` + 折后 expected + 滞后 corrected_total → 三列一致。
2. 扩展 `scripts/verify_fuyi_11col_export.py`：对单把行断言 `L==M==N`（容差 ±0.01）。
3. 附一 strict 样例 Job 导出后抽检「额外外包（纸塑袋）」类单把行。

## 10. 总结

| 项 | 结论 |
|----|------|
| **问题性质** | 账单导出层三列价格解析不一致，非单纯「规则算错」 |
| **直接原因** | 单把行 L 列绑定 `importUnitPrice`（DB unit_price），M/N 列绑定 `resolveExportTotal`；后者在 corrected_total 滞后时回退原价 |
| **为何多把行正常** | 把数>1 时 L 列强制由总价反推，与 M/N 同源 |
| **共性** | **附一 11 列 + 单把行 + 折后单价已落库/总价未回写 + export-v2** 高发；其他医院无第三列，表现不同 |
| **严重程度** | P0：同行三列矛盾，汇总行总价与明细折后口径也可能不一致，财务无法直接采信 |
| **建议优先级** | P0 修导出解析 + 附一 Job 批量重算 corrected_total；中期补双字段落库 |
