## 五、生产环境：「手术室」与 customerCode

### 5.1 名称解析链路

```
导入 Excel
  sheet 名 = 「手术室」  →  ReconciliationHospitalNameResolver 判定为科室名，跳过
  文件名 = 「汽轮机6月账单.xlsx」  →  inferFromFileName → 「汽轮机」
  CustomerResolver.resolveByName("汽轮机")
    → 命中别名 aliases["汽轮机"]
    → customer.code = GUOYAO-MAIN
    → job.hospitalName 规范化为「国药总医院主院区」
  PricingRuleCompiler.compileForCustomer(GUOYAO-MAIN)
    → 应用「国药主院10mm30度镜固定价」等规则
```

相关代码：

- `backend/.../ReconciliationHospitalNameResolver.java` — 科室名过滤 + 文件名推断
- `backend/.../CustomerResolver.java` — 别名解析
- `backend/.../PricingRuleCompiler.java` — 按 customer 编译规则

### 5.2 导出阶段名称替换

`ExportNameMappingApplier` 在**导出**时将行内「哈尔滨汽轮机医院」替换为「国药总医院主院区」（`exportNameMapping`），**不影响计价**。

## 六、为何用户会看到「两家医院」

这是**三套命名并存**造成的认知冲突，而非两套 CODE 并存：

| 场景 | 显示名称 | 实际 CODE |
|------|---------|-----------|
| 特殊收费 Excel 段落 | 哈尔滨汽轮机医院 | （无 CODE 列，导入时映射 GUOYAO-MAIN） |
| 系统客户管理 / baseline | 国药总医院主院区 | `GUOYAO-MAIN` |
| 规则引擎规则名 | 国药主院10mm30度镜固定价 | `GUOYAO-MAIN` |
| 原始发货/账单文件 | 汽轮机N月账单.xlsx | 解析后 → `GUOYAO-MAIN` |
| 处理后账单/结款函 | 国药总医院主院区 | `GUOYAO-MAIN` |

用户看到「汽轮机医院的数据」与「国药主院规则名」同时出现，**看起来像两家医院被错误合并**；按铂康材料，这是**同一计费主体在不同生命周期/文档层的称谓**。

## 七、是否属于数据模型 Bug？

### 7.1 按现有业务材料：**不是误合并**

- 自系统首版种子（2026-07-17）即有明确别名与 exportNameMapping
- 测试材料成对归档（汽轮机原始 ↔ 国药主院处理后）
- 需求文档、逐院登记表、S8 对账均按同一客户验收
- 无第二套汽轮机 CODE、baseline、种子曾存在或被删除的记录

### 7.2 若业务方确认「现已分家」：**则是模型缺陷**

需与铂康/客户确认以下事实之一：

1. **仍是一家**（汽轮机厂医院已并入/托管至国药总院主院区）→ 维持现状，仅需改善 UI/规则命名可读性
2. **已是两家独立签约客户** → 必须拆分，当前映射会导致汽轮机账单错误套用国药主院规则
