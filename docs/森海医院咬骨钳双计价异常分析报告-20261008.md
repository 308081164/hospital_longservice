| 修正总价 | `correctedTotalPrice` | **20.50**（可编辑） | 仍为账单价，带红色 `!` |

行特征摘要：

- 包名：`咬骨钳-1/双Z2032`（包名含 `/双`，符合森海 Excel「包名称带双」段落）

系统表现：规则单价已显示 **16.5**（说明引擎侧已算出「封顶后」的规则价），但**原单价与修正总价仍为 20.5**，形成「规则对了、应付价没改」的观感，与此前「规则单价 vs 导出/修正列不一致」类问题同族。

## 2. 核心结论（Executive Summary）

| 维度 | 结论 |
|------|------|
| 16.5 从哪来 | 与森海特色规则 **未完整生效** 时，引擎走 **通用高温纸塑袋阶梯 + `minCharge` 封顶 16.5** 的典型结果（`PricingEngine.computeHighTempPaperPlastic`）。 |
| 20.5 从哪来 | 客户原始账单单价；在 **修正总价未按规则单价重算并落库** 时，继续占据 `unitPrice` / `totalPrice` / `correctedTotalPrice`。 |
| 为何两列分裂 | 导入/计价写入了 `expectedUnitPrice=16.5`，但 **`correctedTotalPrice` 仍等于原价 20.5**（或后续被编辑回原价），未满足「规则价 ≤16.5 且修正列同步」的产品预期。 |
| 森海「双」特色规则 | baseline 已配置 `森海双<3按件5.5含包材`（`manualReview`），**命中时应走「人工核对 + 暂按账单原价」或按件 5.5 叠包材** 路径；当前行表现为 **标准封顶 16.5**，强烈暗示 **特色 `/双` 规则未作为 special 命中**（或命中后被标准路径结果覆盖展示）。 |
| 性质 | **规则分层 + 字段落库 + 人工核对策略** 叠加导致的可复现行为，不是单点 UI 渲染错误。 |

## 4. 计价引擎：为何会出现「规则 16.5、修正仍 20.5」

### 4.1 对账表四列与 DB 字段

前端列顺序固定为：`unitPrice` → `expectedUnitPrice` → `totalPrice` → `correctedTotalPrice`（见 `ReconciliationDataTable.vue`）。  
红色 `!` 来自 `hasUnitPriceMismatch` / 校验备注（规则单价与原单价不一致）。

### 4.2 路径 A：特色「双」规则命中 + `manualReview`（设计行为）

当 `findSpecialFixedPrice` 命中 `森海双<3…` 且 `manualReview=true` 时：

```307:314:backend/src/main/java/com/hospital/backend/service/PricingEngine.java
            if (isManualReviewSpecialPrice(specialPrice)) {
                requiresReview = true;
                Double billUnitPrice = resolveBillUnitPrice(unitPrice, totalPrice, packCount);
                if (billUnitPrice != null && billUnitPrice > 0.001) {
                    expectedUnitPrice = billUnitPrice;
                }
                notes.add(PRICING_ALERT_PREFIX
                        + buildManualReviewAlert(specialPrice.ruleName, expectedUnitPrice));
            }
```

单测明确要求森海 `/双` 行在人工核对下 **`expectedUnitPrice` 保留账单单价**（如 22 元），`pricingPath=preserve`，状态 `warning`：

- `PricingEngineManualReviewTest#senhaiDoubleBagSlashRuleMarksManualReviewAndPreservesBillPrice`

**若本路径生效，规则单价列应接近 20.5，而不是 16.5。**  
截图规则价为 **16.5**，说明本行更可能 **未走「特色 + 人工核对保留原价」**，而是走了下面的路径 B。

### 4.3 路径 B：特色未命中 → 标准高温纸塑（封顶 16.5）

器械数 1、高温纸塑袋 20cm、包名含「双」时，`computeHighTempPaperPlastic` 对 **&lt;3 件** 计算件费 + 袋费后：

```1796:1801:backend/src/main/java/com/hospital/backend/service/PricingEngine.java
        notes.add("高温纸塑袋件数 " + instrumentCount + " 件，含袋费 " + fmt(totalWithBag) +
                " 元" + doubleNote + "，封顶 " + fmt(capPrice) + " 元。");
        return Math.min(totalWithBag, capPrice);
```

其中 `capPrice` 来自通用规则 `highTemperature.paperPlastic.minCharge`（默认 **16.5**）。  
这与截图 **规则单价 16.5** 高度一致，pricingRule 备注中通常可见「高温纸塑袋20cm计费」「封顶 16.5」等字样（可在该行「计价详情 / PricingFlowDrawer」中核对）。

### 4.4 为何 `correctedTotalPrice` 仍是 20.5

导入时会把引擎输出的 `correctedTotalPrice` 写入行：

```771:774:backend/src/main/java/com/hospital/backend/service/impl/HospitalReconciliationServiceImpl.java
                row.put("expectedUnitPrice", pr.expectedUnitPrice);
                row.put("correctedTotalPrice", pr.correctedTotalPrice);
                row.put("difference", pr.difference);
                row.put("status", pr.status);
```

在 `recomputeTotalsWhenPriceChanges=true`（默认）且 `expectedUnitPrice=16.5` 时，引擎应得到 `correctedTotalPrice=16.5`。  
**截图仍为 20.5**，常见原因包括：

1. **历史版本导入**：在 `expectedUnitPrice` 与 `correctedTotalPrice` 不同步的旧逻辑下导入，仅更新了规则单价列；
2. **未执行或未落库「一键修正」**：`reprice` + `applyBatchCorrection` 会把修正总价设为 `expectedUnitPrice × 包数`（见 `HospitalReconciliationServiceImpl.applyBatchCorrection`），若仅预览未 PUT 保存则 DB 不变（见 `docs/对账规则单价与导出不一致分析报告-20261004.md`）；
3. **人工在「修正总价」列改回 20.5** 且未再次保存；
4. **部分重算**只刷新了 `expectedUnitPrice`（例如仅重跑编排器某层），未触发 `applyBatchCorrection`。

无论哪种，**导出与结算读的是 `correctedTotalPrice`（或回退原价）时，都会继续按 20.5 出账**，与规则列 16.5 背离。

## 5. 根因分析：为何特色「双」规则可能未命中

在「规则价已是 16.5」的前提下，特色规则未命中是解释矛盾的关键（否则 manualReview 会把规则列抬到 20.5）。

| 可能原因 | 说明 | 建议核查 |
|----------|------|----------|
| **类型门控 `acceptedTypes`** | 规则限定 `额外包（纸塑袋）`；若账单 `type` 被录成简称、空值或与注册表不等价，特色规则被跳过。 | 打开该行详情看完整 `type`；对照 `PackTypeRegistry.packTypeEquivalent`。 |
| **客户解析 / 规则编译** | 对账 `importAndProcess` 依赖 `customerResolver.resolveByName(hospitalName)` 再 `compileForCustomer`；若任务医院名与 `哈尔滨森海医院` 不一致，可能落到**无森海 specialRules** 的通用 JSON。 | 查 job 的 `hospitalName`、客户 code 是否为 `SENHAI-YY`。 |
| **关键词竞争 / 优先级** | 森海仅 5 条 productRules，`/双` 规则 priority 9–11；若未命中则落入标准阶梯。 | 计价详情中 `matchedRuleId` / `pricingRule` 是否含「森海双」。 |
| **器械数条件** | `maxInstrumentCount: 2` 对器械数 1 应命中「&lt;3」分支；若器械数被录错为 ≥3，会走免包材分支。 | 核对器械数列与 Excel 原行。 |
| **Excel「16.5 封顶」未建模在特色规则上** | 即使命中特色 `5.5 + 包材`，引擎叠包材路径**未必**与 Excel 同一封顶语义；未命中时只能靠标准 `minCharge` 得到 16.5。 | 产品上需明确：封顶是特色规则属性还是标准阶梯属性。 |

## 6. 与「人工核对（manualReview）」的产品张力

森海、奥兰、远东、电机厂等多家医院的「双 &lt;3 含包材」规则均带 `manualReview`，设计意图是：

- **规则命中**，但单价敏感、需人工确认；
- 引擎 **暂按账单原价展示规则单价**，避免自动改价造成纠纷（见 `buildManualReviewAlert` 文案）。

客户本次诉求是：**规则已明确封顶 16.5，系统应直接按 16.5 修正，而不是保留 20.5。**

这与当前 `manualReview` 策略存在张力：

- 若坚持 manualReview：规则列应贴近 **原价**（20.5），而不是 **16.5**；
- 若规则列已是 **16.5**：说明实际走的是 **标准封顶**，特色 manualReview **未生效**，修正列又未同步，形成「双错层」体验。

## 7. 字段一致性与其他干扰（截图 tooltip）

截图 tooltip 出现 **另一包名**（如 `旋切器-18 盒-1/W12050`），而单元格展示为 `咬骨钳-1/双Z2032`，提示可能存在：

- 包名 / 类型 / 包材 / 器械数 **字段一致性** 告警（`billingNotes.field_consistency`）；
- 计价仍可能按**展示包名**匹配 `/双`，但人工核对成本上升。

建议在「计价详情」抽屉查看 `billingNotes` 与 `PricingFlowDrawer` 时间线，确认匹配关键词与计件数来源。

### 8.1 本行数据核对（只读）

- `expectedUnitPrice`、`unitPrice`、`correctedTotalPrice`、`difference`、`status`
- `pricingRule`、`pricingPath`、`matchedRuleId`

**期望对照：**

| 场景 | expectedUnitPrice | correctedTotalPrice | pricingRule 关键词 |
|------|-------------------|---------------------|-------------------|
| 特色 + manualReview 命中 | ≈20.5 | 未修正前≈20.5 | 森海双 |
| 标准高温封顶 | 16.5 | 应 16.5（若已修正） | 高温纸塑袋…封顶 16.5 |
| 客户期望（修正后） | 16.5 | **16.5** | 森海双 或 标准封顶 |

### 8.2 规则试算（需绑定客户）

生产 `POST /api/v1/billing-rules/simulate` 要求 `customerId`；若客户「未绑定默认计价规则」会 400。对账导入则使用 **任务医院名 + compileForCustomer**，与 simulate 入口不一致，**不能以 simulate 失败否定对账计价**。

### 8.3 操作修复（业务）

1. 确认医院解析为 **哈尔滨森海医院 / SENHAI-YY**；
2. 对该 job 执行 **一键修正**（当前版本会 **自动落库** `correctedTotalPrice`）；
3. 导出前关注导出向导 **「规则价未落库」** 提示（`unpersistedRulePriceRows`）；
4. 若仍不对，检查 `type` 是否为 `额外包（纸塑袋）` 规范写法。

## 11. 一句话总结
