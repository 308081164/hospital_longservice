# 对账「规则单价已正确、导出仍为原价」问题分析报告

**报告日期：** 2026-10-04  
**问题来源：** 客户反馈（妇科门诊 · 人流包等行）  
**分析范围：** 医院 Excel 对账 → 规则计价 → 账单导出全链路  
**代码基线：** `main`（含内勤三层计价 `ReconciliationPricingOrchestrator`、`BillExportPriceResolver`）

---

## 1. 问题现象（客户截图还原）

### 1.1 对账页（系统内）

| 字段 | 典型表现（以「人流包」为例） |
|------|------------------------------|
| 原单价 | `88.00` |
| **规则单价** | `40.00`（带红色叹号，表示与原单价不一致） |
| 原总价 | `88.00` |
| **修正总价** | `-`（空） |
| 状态 | 多为 `unchanged`，但落在「仅异常」筛选内（`price_mismatch`） |

顶部汇总示例：待复核 134 行、修正价与原总价存在差额，但「修正」计数可能仍为 0。

### 1.2 导出 Excel（客户账单）

同一科室 sheet（如「妇科门诊」）中，**单价列仍为 `88.00`**，与对账页规则单价 `40.00` 不一致。

客户结论：**「规则已经读对了，导出的数据却没有」** —— 从用户视角完全合理；从系统实现看，这是**展示层与落库/导出层字段口径分裂**导致的可复现缺陷，而非规则引擎未运行。

---

## 2. 核心结论（Executive Summary）

| 维度 | 结论 |
|------|------|
| 规则是否生效 | **是**。`expectedUnitPrice`（规则单价）已在导入/计价阶段写入数据库，UI 直读该字段。 |
| 为何 UI 与导出不一致 | **多条链路叠加**：① 内勤计价只写规则单价、不写修正总价；② 账单导出依赖「行匹配 + 价格解析器」，匹配失败时保留原 Excel 价格；③ 对账与导出各跑一套内勤规则，且导出不读对账页开关；④ 一键修正/重定价可能只更新前端未落库。 |
| 最可能根因（本案例） | **原始文件导出路径 `generateBillFromOriginalFile` 行匹配失败**，未覆盖单价单元格，原文件 `88.00` 被保留；同时 DB 中 `correctedTotalPrice` 为空，加剧「修正总价为空、导出仍像原价」的观感。 |
| 性质判定 | **实现缺陷 / 数据模型不一致**，不是客户误操作，也不是「规则未配置」。 |

## 3. 数据模型：三个价格字段各司其职

对账行在 DB（`hospital_reconciliation_row`）与 API 中同时存在三套价格语义：

| 字段 | 业务含义 | UI 列 | 导入内勤计价典型值 | 账单导出是否优先使用 |
|------|----------|-------|-------------------|---------------------|
| `unitPrice` / `totalPrice` | 客户原始账单价 | 原单价 / 原总价 | 保持 Excel 原价 | 仅作回退 |
| `expectedUnitPrice` | 规则/内勤计价结果 | **规则单价** | 内勤命中时写入（如 40） | **优先**（经 `BillExportPriceResolver`） |
| `correctedTotalPrice` | 按规则重算后的应付总价 | **修正总价** | 内勤路径常为 **null** | 次优先；为 null 时用 `expectedUnitPrice × 包数` 重算 |

**关键分裂点：** 对账页把「规则单价」和「修正总价」展示为两列，但**内勤计价命中时只保证前者**：

```60:69:backend/src/main/java/com/hospital/backend/service/ReconciliationPricingOrchestrator.java
if (clerkPrice.isPresent()) {
    // ...
    result.expectedUnitPrice = unitPrice;
    result.pricingRule = "内勤计价：" + clerkRuleName;
    result.status = "unchanged";
    // 未设置 correctedTotalPrice / difference
}
```

因此客户看到：**规则单价 40 ✓、修正总价空 ✗** —— 这是当前实现的**预期副作用**，不是偶发渲染错误。

## 4. 全链路数据流

```
[Excel 上传]
     │
     ▼
importAndProcess
     ├─ ReconciliationPricingOrchestrator.processRow
     │    ├─ 内勤计价命中 → expectedUnitPrice ✓, correctedTotalPrice ✗, status=unchanged
     │    └─ 客服引擎路径   → expectedUnitPrice ✓, correctedTotalPrice ✓（视 recompute 配置）
     ├─ 直接 row.put（未调用 applyBatchCorrection）  ← 与 reprice 路径不一致
     ▼
hospital_reconciliation_row（DB）
     │
     ├─► GET /rows → 前端表格
     │      ├─ expectedUnitPrice  → 「规则单价」+ price_mismatch 叹号
     │      └─ correctedTotalPrice → 「修正总价」（常为空）
     │
     ├─► POST /reprice（一键修正）
     │      ├─ applyBatchCorrection → 补全 correctedTotalPrice
     │      └─ 若仅 repriceAndStage → 前端 pending，未 PUT 保存则 DB 不变
     │
     └─► POST /export-v2（账单导出）
            ├─ ReconciliationExportDataLoader（读 DB）
            ├─ BillExportRequestMapper + BillExportPriceResolver（预解析导出价）
            ├─ ClerkRuleExportService.applyBillExportRules（导出阶段再次跑内勤规则，写 unit/total）
            └─ generateBillExportBytes
                   ├─ 主路径：程序化/标准模板 + writeSheetFromTemplate（用 Resolver 写价）
                   └─ 降级：generateBillFromOriginalFile（按 key 匹配原 Excel 行后改价）
```

**对账计价与导出计价是两次独立执行：**

- 对账：`ReconciliationPricingOrchestrator`（可读 job 的 `pricing_rule_overrides` 关闭 clerk 层）
- 导出：`ClerkRuleExportService` → `ClerkBillPriceRuleApplier`（**不读**对账页两个总开关）

## 5. UI 为何「看起来规则对了」

### 5.1 规则单价列

前端 `ReconciliationDataTable` 直接绑定 `expectedUnitPrice`，数据来自分页 API，**不做二次计算**。

### 5.2 红色叹号

`hasUnitPriceMismatch`：当 `|unitPrice - expectedUnitPrice| > 0.001` 时告警 —— 正好对应「原价 88、规则价 40」。

```39:45:frontend/src/utils/reconciliationAnomaly.ts
export function hasUnitPriceMismatch(row: Record<string, unknown>): boolean {
  const unitPrice = toNumber(row.unitPrice ?? row.unit_price)
  const expectedUnitPrice = toNumber(row.expectedUnitPrice ?? row.expected_unit_price)
  if (unitPrice == null || expectedUnitPrice == null) return false
  return Math.abs(unitPrice - expectedUnitPrice) > PRICE_TOLERANCE
}
```

### 5.3 修正总价为空

内勤导入未写 `correctedTotalPrice`；且 `status=unchanged`（内勤分支硬编码），不会走 `applyBatchCorrection` 的「有差价则 corrected」逻辑。

### 5.4 导入 vs 重定价路径不一致

| 阶段 | 是否调用 `applyBatchCorrection` |
|------|--------------------------------|
| `importAndProcess` | **否** — 仅 `row.put(pr.*)` |
| `reprice` / `repriceRow` | **是** — 会补 `correctedTotalPrice` |

row.put("correctedTotalPrice", pr.correctedTotalPrice);  // 内勤路径常为 null

## 6. 导出链路深度分析

### 6.1 账单导出（export-v2 / export-template-bill）

**设计上**应使用规则价：`BillExportPriceResolver` 在 `expectedUnitPrice` 存在时，即使 `correctedTotalPrice` 为空，也会重算导出总价：

```119:138:backend/src/main/java/com/hospital/backend/export/BillExportPriceResolver.java
static Double resolveExportTotal(...) {
    if (expectedUnitPrice == null) { /* 回退 corrected → total */ }
    Double recomputed = round(expectedUnitPrice * packs);
    if (correctedTotalPrice == null) {
        return recomputed;  // ← 专为此类 import 遗留问题设计
    }
    // corrected 与重算不一致时，以 expected 为准
    return recomputed;
}
```

`BillExportRequestMapper.toBillRowItem` 与 `loadBillRowsFromDb` 在映射时**已预解析**并写回 `unitPrice` / `totalPrice`：

```46:55:backend/src/main/java/com/hospital/backend/export/BillExportRequestMapper.java
Double exportUnit = BillExportPriceResolver.resolveUnitPrice(row);
Double exportTotal = BillExportPriceResolver.resolveTotalPrice(row);
if (exportUnit != null) { item.setUnitPrice(exportUnit); ... }
if (exportTotal != null) { item.setTotalPrice(exportTotal); ... }
```

**因此：若导出仍显示 88，说明「写价步骤」未作用到该行**，而非 Resolver 不存在。

### 6.2 根因 A：原始文件导出 + 行匹配失败（本案例高概率）

当标准模板导出异常时，系统降级到 `generateBillFromOriginalFile`：打开**客户上传的原始 xlsx**，按 key 查找行后改写单价/总价。

匹配 key（**不含发货日期、行号**）：

```3810:3816:backend/src/main/java/com/hospital/backend/service/impl/HospitalReconciliationServiceImpl.java
private String buildRowMatchKey(BillRowItem item) {
    return joinFields(
        item.getOrderNo(), item.getCategoryNo(),
        item.getType(), item.getPackName(), item.getPackageMaterial());
}
```

**匹配失败时：不修改该 Excel 行 → 保留原价 88。**

常见失败原因：

| 原因 | 说明 |
|------|------|
| 发货单号格式 | DB 字符串 `1631884` vs Excel 数值单元格 `1631884.0` / 科学计数 |
| 类型字段截断 | UI/DB 存 `额外包 (纸塑...)`，原表完整文案不一致 |
| 包类别号列名 | 原表用「病人ID」等别名，映射失败 |
| Sheet 名不一致 | 分组 key 对不上，整表跳过 |
| 同 key 多行 FIFO | 同名「人流包」多行、字段相同但价格不同，deque 顺序错配 |

客户截图中同一 sheet 内「人流包」同时存在 **40** 与 **88** 两种单价，更增加**错配或未匹配**风险。

### 6.3 根因 B：一键修正仅预览、未保存

`repriceAndStage` 将结果放入 `pendingRepricedRows`，**必须点「保存修改」**才 PUT 到 DB。导出始终读 DB → 若用户未保存，导出仍为旧数据。

（本案例中 UI 已显示规则单价 40，说明 DB 里 `expectedUnitPrice` 大概率已有值；此根因为次要，但在线上需排查操作顺序。）

### 6.4 根因 C：对账与导出「双轨内勤规则」

| | 对账导入/重算 | 账单导出 |
|--|--------------|----------|
| 入口 | `ReconciliationPricingOrchestrator` | `ClerkRuleExportService.applyBillExportRules` |
| 写字段 | `expectedUnitPrice` + billingNotes | 主要写 `unitPrice` / `totalPrice` |
| 对账页开关 | 读 `pricing_rule_overrides` | **不读** |

导出阶段 `ClerkBillPriceRuleApplier.apply` 按包名/类型/包材等匹配，**可能命中与对账不同的规则或根本不命中**。但由于 Resolver 优先 `expectedUnitPrice`，正常 export-v2 仍应以 DB 规则价为准 —— **除非行未写入（匹配失败）或 expected 为空**。

### 6.5 根因 D：异常导出不走 Resolver

`export-anomalies` 直读 DB：

```1882:1885:backend/src/main/java/com/hospital/backend/service/impl/HospitalReconciliationServiceImpl.java
String corrUnitPrice = row.getExpectedUnitPrice() != null ? ... : "";
String corrTotalPrice = row.getCorrectedTotalPrice() != null ? ... : "";
```

若客户导出的是「异常明细」而非账单，会出现**修正单价有值、修正总价空白** —— 与 UI 一致，但不是账单格式问题。

### 6.6 根因 E：汇总行金额仍用旧逻辑

`generateBillFromOriginalFile` 汇总 `totalAmount` 时：

```3467:3470:backend/src/main/java/com/hospital/backend/service/impl/HospitalReconciliationServiceImpl.java
if (matched.getCorrectedTotalPrice() != null) {
    totalAmount += matched.getCorrectedTotalPrice();
} else if (matched.getTotalPrice() != null) {
    totalAmount += matched.getTotalPrice();
}
```

在 Mapper 已把 `totalPrice` 设为解析后总价的前提下，匹配成功时汇总可对；**匹配失败则整行仍按原价累计**。

## 8. 影响面评估

| 影响项 | 说明 |
|--------|------|
| 财务风险 | 对外账单可能按原价出账，与内勤价表/合同约定不一致 |
| 运营信任 | 对账页显示「规则已对」，导出却不对，引发「系统不可信」 |
| 统计偏差 | `status=unchanged` + `correctedTotalPrice=null` 导致任务级「修正行数/修正价」偏低 |
| 异常筛选 | 大量行进 `price_mismatch`，但无自动修正总价，人工难以判断「是否已生效」 |

## 9. 修复建议（按优先级）

### P0 — 导入与内勤计价对齐（治本）

1. **`importAndProcess` 末尾对每行调用 `applyBatchCorrection`**，与 `reprice` 一致，确保 `correctedTotalPrice`、`difference`、`status` 落库。
2. **`ReconciliationPricingOrchestrator` 内勤分支**：在设置 `expectedUnitPrice` 后同步计算 `correctedTotalPrice` 与 `difference`，有差价时 `status=corrected`（或至少 `warning`）。

### P0 — 导出行匹配加固

1. `buildRowMatchKey` 增加 **发货日期**、必要时 **行号** 作为 tie-breaker。
2. 发货单号/包类别号统一 **规范化**（去小数尾 `.0`、科学计数转字符串）。
3. 匹配失败时 **打日志 + 导出校验报告**（列出未写价行数），禁止静默保留原价。
4. 降级原文件导出失败率监控：模板导出失败应告警，而非无声 fallback。

### P1 — 导出与对账规则一致

1. `ClerkRuleExportService` 读取 job `pricing_rule_overrides.disabledCategories`。
2. 导出阶段避免覆盖已由 DB `expectedUnitPrice` 确定的行（或统一以 Resolver 最终值写 Excel）。

### P1 — 异常导出与 UI 一致

1. `exportAnomalies` 的修正总价列改用 `BillExportPriceResolver.resolveTotalPrice`。

### P2 — 产品体验

1. `correctedTotalPrice` 为空但 `expectedUnitPrice` 有值时，UI 展示**推算修正总价**（或导入后即补全，不依赖前端推算）。
2. 存在 `pendingRepricedRows` 未保存时，导出前强提示或阻断。
3. 内勤命中但 `status=unchanged` 时，在状态列区分「内勤价已覆盖原价」。

## 12. 总结陈述（可对客户说明）

> 系统**已经**根据内勤/计价规则算出了正确的规则单价（40 元），并在对账页展示；但导入时**没有把该价格同步写入「修正总价」**，且账单导出在部分情况下会**按原 Excel 行做键值匹配再改价**——匹配失败时仍保留客户文件里的原价（88 元）。因此会出现「页面上规则对了、导出文件还是错的」的现象。这是当前版本在**数据落库与导出写价**上的实现缺口，需要通过导入补全修正价、加固导出行匹配和统一对账/导出规则口径来修复。
