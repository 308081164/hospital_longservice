# 结款函格式与折扣问题分析及处理方案

日期：2026-10-21。对照客户 10 月 20 日聊天、四张结款函截图，以及 10 月 21 日附一折扣确认。按本文方案改代码。

奥兰的规则客户说要另找时间沟通，不在本文范围内。

## 结论

1. 字号不是问题。客户说「直接这样就可以了」，指的是样张那种写法：低消不要单独成行，写在合计备注里。
2. 悦美芳华的低消金额是对的（836 + 150 = 986，补 14，合计 1000）。多出来的是「低消补差」这一行。样张把差额吸收进合计，备注写「执行低消1000元」。
3. 山河屯没有物流费，费用只剩灭菌一行。模板按两行费用排版，少一行时不挪动后面的正文，再把原来的合并单元格拆开，说明文字掉进很窄的一列，于是逐字竖排。金额 2910.50 本身没有算错。
4. 工程大学九折只应出现在结款函，不会改对账行单价。规则能挂上时，灭菌费会乘 0.9。备注函数把 0.9 写成「90折优惠」，不是「九折优惠」。客户看到的「没体现」，就是这句备注不像九折；若灭菌费仍是原价，则是导出时没有编进 `HRB-HEU` 的结款折扣。
5. 中医药大学附属第一医院的对账叠折，第二段由 0.99 改为 0.999。第一段仍是 0.8。只改这一家。

## 1. 悦美芳华：不要「低消补差」这一行

### 客户原话和两张函

系统函（2026-09）：

| 条目 | 费用 | 备注 |
|---|---|---|
| 灭菌费用 | 836.00 | |
| 物流费用 | 150.00 | 50.00/次 |
| 低消补差 | 14.00 | 低消 1000.0 |
| 合计 | 1000.00 | （空） |

样张：

| 条目 | 费用 | 备注 |
|---|---|---|
| 灭菌费用 | 836.00 | |
| 物流费用 | 100.00 | 50元/次 |
| 合计 | 1000.00 | 执行低消1000元 |

聊天里先问是不是字号，客户接着说不需要一行写抵消补差，并给出上面这张样张。红框只框了「低消补差」那一行。

样张物流是 100（两次 × 50），系统是 150（三次 × 50）。这是趟次不同，不是低消算法。这次不改物流单价，仍是 50 元/次。

### 代码为什么会多一行

低消规则在 `YUEMEI-FH.json`：`SETTLEMENT_MIN_CHARGE`，基数是灭菌费加物流费，不满 1000 补到 1000。836 + 150 = 986，补差 14，合计 1000。这个数和系统函一致。

写出这一行的位置在 `SettlementTemplateFiller`：月结分解里的 `adjustment` 绝对值不小于 0.01 时，正数记「低消补差」，备注「低消 1000」。`BillingPolicyInspector.settlementOmitMinChargeRow` 只有在规则参数带 `settlementOmitMinChargeRow` 或 `settlementDisplayMode=embed` 时才跳过。悦美芳华的规则没有这两个参数，所以一定出这一行。

合计行的备注被写死成空。`HospitalReconciliationServiceImpl.writeSettlementTemplate` 在合计行把备注列设为 `null`，所以「执行低消1000元」现在没有地方可写。

### 处理方案

只改结款函的展示，不改低消基数，也不改 1000 这个门槛。

- 悦美芳华（以及同样希望「低消写在合计上」的医院）不再输出「低消补差」行。
- 合计金额仍是补差之后的应付额。上例是 1000.00。
- 合计备注写「执行低消1000元」。超过 1000 时不补、不写这句，和规则原文「超过则正常收费，不更改结款函收费」一致。
- 实现上给该院月结参数加上已有的 `settlementDisplayMode=embed`（或 `settlementOmitMinChargeRow`），并在合计行写入备注。现在 `settlementOmitMinChargeRow` 为真时，后面还有一段用 `job.settlementAdjustment` 再补一行「低消补差」的分支，embed 时必须关掉这段，否则行还在。
- 物流 150 与样张 100 的差别留在趟次上，不把单价改成别的数。

改完验收：灭菌 836、物流 150、没有低消补差行、合计 1000、合计备注「执行低消1000元」。灭菌加物流已经不低于 1000 的月份，没有补差行，合计备注为空。

## 2. 山河屯：正文逐字竖排

### 客户原话和截图

「山河屯医院的结款函格式全没了。」

函上的表还能读：灭菌费用 2910.50，合计 2910.50，大写贰仟玖佰壹拾元伍角。没有物流行。标题和「致：」也在。表下面的「贵医院各个科室……」和落款被拆成一个字一行。

### 代码为什么会竖排

山河屯规则是 `LOGISTICS_WAIVE`，`feePerTrip = 0`。`shouldShowLogisticsRow` 在单价不大于 0 时不输出物流行。费用明细只剩灭菌一行。这符合「没有物流费」，不是把物流费算进灭菌费。

结款函模板预设 **2** 行明细（灭菌、物流），合计从第 14 行起。`writeSettlementTemplate` 用实际行数减 2 得到 `diff`。

- 多出行（悦美芳华有低消补差，是 3 行）会插入行，版式还能守住，所以那张函是齐的。
- 少一行（山河屯）**不删行**。注释写明 `deleteRows` / `shiftRows` 会拆掉模板里的合并区域。代码只清空多出来的明细格，然后按「1 行明细」重算正文所在行，并拆掉模板上 D17:I19 那几段合并。

正文原来靠 D 到 I 的合并才有整段宽度。合并拆开后，这段话留在很窄的 D 列，自动换行就变成一字一行。落款同一原因。所以看起来是「格式全没了」，数字并没有丢。

凡是结款函只有一行费用的医院都会走这条路径，不只有山河屯。没有物流费、或物流费为 0 且被省略的医院都一样。

### 处理方案

费用行数少于模板的 2 行时，正文、敬语、落款仍要落在合并后的宽单元格里。

- 少行时不要先拆掉模板正文的 D:I 合并，再把文字写到另一行的窄列。
- 要么把合计、大写、正文整段上移到紧贴这一行灭菌费的位置，并重新合并 D:I；要么保留模板行距，但正文仍然写进已经合并的 D:I。
- 不要用 `shiftRows` 硬删，除非同时按新行号重建全部合并区域。现有注释里的风险还在。
- 山河屯继续不显示物流行，灭菌费保持原额，不乘折扣。

改完验收：只有灭菌一行时，正文是横排段落，落款在右下，表格仍是 2910.50。有灭菌和物流两行的医院版式与现在一致。

## 3. 工程大学：结款函九折没体现成「九折」

### 客户原话

「工程大学的结款函折扣没体现。」没有附函。规则原文是「结款函费用体现为灭菌账单金额的9折」。

### 规则实际怎么挂

`HRB-HEU.json` 是 `SETTLEMENT_DISCOUNT`，`rate` 0.9，`target` sterilize，阶段 settlement。编译后是 `applyStage=settlement_only` 的折扣。历史种子写明：这 9 折只用于结款函，不能进账单计价和账单导出。对账行单价保持原价是预定行为，不是这次漏折。

正式结款函走 `ExportEngineServiceImpl.buildSettlementExportRequest`：按医院名解析客户编码，`mergeCompiledForSettlement` 把内勤策略并进规则，再交给 `buildFeeRows`。编码对上 `HRB-HEU` 时，灭菌费显示为原额 × 0.9，合计跟着变。别名包括「哈尔滨工程大学医院」「哈尔滨工程大学」「工程大学医院」，以及账单表头里的「哈尔滨(工程)大学医院」「哈尔滨（工程）大学医院」。名字对不上编码时，这段折扣不会并进去，函上就是全额、备注为空。

### 备注写成了「90折优惠」

`BillingPolicyApplier.formatSettlementDiscountRemark` 对 0.7、0.75、0.5 有中文（七折、七五折、五折）。0.9 没有。它用 `rate × 100` 得到 90，拼成「90折优惠」。

单测 `settlementOnlyDiscountRemarkIsShortLabel` 期望的是「九折优惠」，金额是 10000 → 9000。当前这个函数在 0.9 上返回的是「90折优惠」，和单测、和客户说的九折都不是同一句。客户说「没体现」，指的就是函上没有可识别的九折说明。金额若已是九折，客户仍会觉得折扣没写上；金额若仍是原价，则是医院名没有解析到 `HRB-HEU`，折扣策略根本没并进这次导出。

### 处理方案

- 0.9 的结款备注改为「九折优惠」，与 0.7、0.75 同一套中文，不要再用「90折优惠」。
- 灭菌费行金额保持原额 × 0.9，备注用这句。合计用折后灭菌费加物流费，物流费不打折。
- 不把九折乘进对账行，也不要改 `HRB-HEU` 的 0.9。
- 导出前确认医院名能解析到 `HRB-HEU`。解析失败时函上不打折，这和「没体现」是同一现象，要在导出日志里能看到没并进结款策略。

改完验收：灭菌费 10000 的函显示 9000，备注「九折优惠」。账单导出里同一批明细的单价不变。

## 4. 中医药大学附属第一医院：0.8 × 0.999

### 现象

对账追溯步骤 7：命中「附一对账八折 + 附一对账九九折」。基础规则单价 11.00 元 → 11.00 × 0.8 = 8.80 元 → 8.80 × 0.99 = 8.71 元。步骤 8 字段核对：规则单价 8.71 元与原账单价 8.80 元不一致，请人工复核。

### 客户原话（微信，小喵确认）

「中医药大学附属第一医院的问题是这款是 0.8*0.999 折扣」。对方确认「也就是 0.8*0.99 改成 0.8*0.999 是吗？」小喵答「是的」。

### 原因

`ZYY-D1`（黑龙江中医药大学附属第一医院）`billingPolicies` 第二段「附一对账九九折」系数仍是 0.99，叠乘后比客户账单口径少约一角。第一段八折 0.8 无误。

### 修改方案

- 只改 `backend/src/main/resources/billing-rules/baseline/ZYY-D1.json` 第二段：费率 0.99 → 0.999，名称改为「附一对账九九九折」，`sourceRef` 记 `wechat:2026-10-21`。
- 八折 0.8 不动；不改其他医院的九九折。
- 按规范重算 `billing-rules/index.json` 与 `billing-rules-manifest.json`（`refresh_baseline_index.py` + `baseline_to_manifest.py --write`），禁止手改 hash、禁止从旧 Excel 整表重生。

### 改完后演算

两步各自四舍五入到分：

1. 11.00 × 0.8 = 8.80
2. 8.80 × 0.999 = 8.7912 → 显示单价 **8.79**

账单原价 8.80 与改后 8.79 仍差 1 分。本次按客户确认的 0.999 落库，不另写把 8.79 收成 8.80 的规则。

### 验收标准

1. 单测：基础价 11，命中八折+九九九折后显示单价为 8.79，说明含 0.999 与中间步 8.80。
2. 旧口径 8.71（×0.99）断言全部改为新口径。
3. 本地 8088 导入/计价入口对附一叠折链能看到 0.8 × 0.999，不再出现 ×0.99 → 8.71。
4. 生产部署后 `version` 对齐本次 commit；规则基线含 `ZYY-D1` 第二段 rate=0.999。

## 处理顺序

1. 工程大学备注改成「九折优惠」。金额口径已经是 × 0.9，不改折扣率，也不乘进对账行。
2. 悦美芳华去掉「低消补差」行，合计备注写「执行低消1000元」，合计仍是补足后的金额。
3. 费用只有一行时，正文先挪进新的宽合并格再拆开旧格，山河屯函恢复横排。不增加物流行。
4. 附一第二段折扣改为 0.999。

奥兰等客户另约之后再改。
