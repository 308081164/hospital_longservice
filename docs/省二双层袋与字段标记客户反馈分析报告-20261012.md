## 1. 结论

客户看到的三类现象是三套独立缺陷叠在一起，不是同一次改价就能消掉。

1. **双层袋价格错，主因是规则文件已更新，代码和种子仍按旧口径。**  
   黑龙江省第二医院（松北）被 `isHrb2ndHospital()` 当成「市二院」，低温单件「双」没有走通用规则「固定 35 元」。纸塑「双」仍套用全局 16.5 封顶，以及「≥3 件袋费全免」。客户 Excel 写明松北 **没有不超过 16.5 的规则**。2026-10-12 客户又补充：宽度大的是外层；＜3 件的标准包材是材料列里全部袋子的价格（两只就收两只），≥3 件只加较宽的外层。代码按材料列书写顺序定内外层，和这条相反。详见第 2.1 节。
2. **颜色有的有、有的没有，是因为整行底色只绑字段核对，不绑差额。** 单价不一致只出感叹号。内勤计价命中时引擎根本不跑，字段核对也不会着色。人工标成「无需修改」后，底色和单元格色都会被清掉。
3. **感叹号气泡经常在解释另一件事。** 气泡只拼接字段核对原文。单价不一致、未命中规则时，气泡退回一句「字段核对未通过」，和真实原因不符。计价过程里的「已按账单原价暂计」「规则单价 30 与原账单 24.50 不一致」写在七折和袋费叠加之前，和最终「规则单价」列不是同一个数。
4. **科室标签后面的异常数被折扣改写状态后清掉了。** 标签上的灰色数字是该科室总行数，琥珀色数字才是异常数，而且只统计 `status = warning`。内勤折扣一改单价，编排器就把状态改成 `corrected` 或 `unchanged`。省医院香坊因此是「修正 433、待复核 0」，科室问题高亮全部消失。客户要求问题高亮保留，**「修正」行也必须计入各科室的问题数**。详见第 6.1 节。

客户要求的顺序是：

1. 字段校验永远第一步。不一致就标记，然后继续计价。
2. 内勤计价规则。命中则覆盖特殊收费。
3. 特殊计价规则。
4. 内勤折扣规则。

当前实现把第 1 步放进了 `PricingEngine.processRow`。内勤计价命中时编排器 **不调用引擎**，字段校验被跳过。折扣在编排器最后一步，这一层的位置是对的，但它不看特色规则的 `skipDiscount`，松北「双」规则标了跳过折扣，七折仍会乘上去。字段不一致不会中断计价，这一点和客户要求一致；中断感来自气泡和抽屉把中间价说成最终规则单价。

### 2.1 客户对「双」的两条补充（2026-10-12 09:59 微信）

同日客户高健对「两个包装材料时哪只是外层」和「标准包材价格收几只袋子」作了确认。这两条改写第 2 节表格里「标准包材」「外层纸塑袋」的读法，内外层必须以宽度区分，不能按单元格里的书写顺序。

**补充一：宽度大的是外层，宽度小的是内层。**

包装材料列出现两只袋子时，比较宽度（毫米尺寸里 `*` 前的那个数，如 `100*260` 的宽度是 100，`75*200` 的宽度是 75）。宽度大的那只是外层，宽度小的是内层。书写先后不算数。`75*200，100*260` 的外层是 100mm（10cm），内层是 75mm，即使 75 写在前面。

松北 ≥3 件的「外层纸塑袋的标准包材价格」只加这一只较宽袋子的标准价，不加较窄的内层。

当前 `resolveDoubleBagSizes` 不比宽度。材料列用逗号分成两段时，**第一段当作外层、第二段当作内层**（`PricingEngine.java` 约第 1618–1629 行）。上面这个例子会被收成外层 75、内层 100，和客户口径相反。成人头钉一行材料就是「75*200 + 100*260」，抽屉却按 10cm 计，内外层已经对不上。

只有一段材料、尺寸写在 `/双` 后面时，仍用该尺寸；没有第二只袋子的宽度时，不要把同一只袋子再复制成内层。

**补充二：标准包材是材料列里全部袋子的价格；列出两只就收两只。**

「标准包材价格」不是一只抽象的袋子，也不是 16.5 封顶后的余额。它等于这一格里写出来的每一只袋子的标准袋价之和。

| 件数 | 公式 | 袋子怎么收 |
| --- | --- | --- |
| ＜3 | 5.5×件数 ＋ 标准包材价格 | 材料列有几只袋子就加几只。两只袋子 = 内层标准价 + 外层标准价 |
| ≥3 | 5.5×件数 ＋ 外层纸塑袋的标准包材价格 | 只加宽度较大的那只外层，内层袋费不加 |

＜3 与 ≥3 的差别只在袋子：不满 3 件两只都收；满 3 件只留外层。两边都不封顶 16.5。包名里有「双」但材料列只写了一只袋子时，标准包材就是这一只的价格，不能因为看到「双」就按同一尺寸再加一份。

代码现在的差距：

- ＜3 的特色加袋（`computeHighTempBagAddon`，件数小于 3）会把 `bagFee1 + bagFee2` 相加，只数上接近「两只都收」。内外层若按书写顺序装反，两只的单价就加错了。材料列只有一只、内层解析为 0 时，代码把内层回落成外层尺寸（约第 1633–1635 行），会把同一只袋子算两次。
- ≥3 的标准阶梯把全部袋费免掉。特色加袋在件数 ≥ 3 时优先返回内层袋价（`bagFee2` / `innerBagSize`，约第 2156–2162 行），客户要的是较宽的外层。

### 2.2 同屏另一条：敷料包（所有医院）

同一段对话里客户还确认了一条，不属于「双」的袋费公式，但是全局口径：

> 所有医院的「敷料包」这个类型本来就没有包材。系统不能核对，但是要保留睿思原价，不要在睿思价格基础上再打折。

含义：

- 类型是敷料包时，不做包材尺寸、包材类别、包名件数这一类字段核对，也不要因为包材列为空或对不上就出感叹号、行底色。
- 规则单价保持睿思账单原价。
- 内勤折扣、导出折扣都不要再乘在这个原价上。

当前字段核对只在器械数为 0 且名称像敷料时跳过件数核对（`BillRowFieldConsistencyValidator.shouldSkipInstrumentCountMismatch`）。器械数不为 0 的敷料包仍会核对；折扣编排器也不区分敷料包。

## 3. 校验顺序：客户要求与代码实际路径

### 3.1 客户要求

```
字段校验（不一致则标记，不停止）
    → 内勤计价（命中则覆盖特殊收费）
        → 特殊计价
            → 内勤折扣
```

字段校验不因存在内勤规则而省略。计价不因字段不一致而提前结束。感叹号是计价完成之后的提示，不是计价中断开关。

### 3.2 现在的两条路径

`ReconciliationPricingOrchestrator.processRow`：

- **内勤计价命中**（约第 60–74 行）：直接构造 `ProcessedResult`，`pricingPath=clerk`，**不调用** `engine.processRow`。字段尺寸、包材类别、包名件数都不会跑。随后若内勤折扣命中，仍会乘折扣。
- **内勤计价未命中**：才进入引擎。引擎开头（约第 100–118 行）做字段核对，把 `【字段核对】` 写入 notes，并 `forceConsistencyWarning`。然后才是特色价、标准阶梯、袋费。编排器在引擎返回之后再乘内勤折扣（约第 84–114 行），**不读取** `skipHospitalDiscount`。

因此：

| 要求 | 现状 |
| --- | --- |
| 字段校验永远第一步 | 只在「没走到内勤计价」时成立 |
| 有内勤规则也要做字段校验 | 内勤计价命中即跳过 |
| 字段不一致不结束计价 | 引擎路径满足：警告强制为 `warning`，价格照算 |
| 内勤计价覆盖特殊收费 | 满足（命中后不再进引擎） |
| 特殊计价在内勤折扣之前 | 引擎路径满足 |
| 特色规则 `skipDiscount=true` 时不再打七折 | 不满足。引擎内部医院折扣会跳过，编排器的内勤折扣仍会打 |

引擎在折扣之前写的这句（`PricingEngine` 约第 706–708 行）：

> 【字段核对】规则单价 {引擎价} 元与原账单价 {原单价} 元不一致

这里的「规则单价」是 **七折前、有时还是袋费叠加前** 的中间数。编排器随后改 `expectedUnitPrice`，列上的规则单价变了，这句话不改。抽屉里就会出现「暂按 9.45」或「规则单价 30 与 24.50 不一致」，而表格规则单价已经是 11.55 或 21.00。

## 4. 双层袋算错的三个机制

### 4.1 低温单件「双」把松北当成市二院

```2171:2176:backend/src/main/java/com/hospital/backend/service/PricingEngine.java
    private static boolean isHrb2ndHospital(String hospitalName) {
        if (hospitalName == null || hospitalName.isBlank()) {
            return false;
        }
        return hospitalName.contains("第二医院") || hospitalName.contains("市二院");
    }
```

「黑龙江省第二医院（松北区）」包含「第二医院」，函数返回 true。紧接着的分支被跳过：

```1877:1892:backend/src/main/java/com/hospital/backend/service/PricingEngine.java
        if (instrumentCount == 1 && isDouble && !isHrb2ndHospital(hospitalName)) {
            notes.add("低温单件纸塑袋包名含「双」，按客户标准固定 35 元计费（市二院除外）。");
            return 35.0;
        }
        // ...
            if (isDouble && zBagSize > 0) {
                notes.add("低温单件纸塑袋 " + bagConfig.path("size").asInt() + "cm，单件计费忽略包名「双」追加袋费，单价 "
                        + fmt(price) + " 元。");
```

Excel 的除外对象是 **市二院**（哈尔滨市第二医院），不是省二。松北低温单件「双」应固定 35 元，再走内勤七折：35 × 0.7 = **24.50**。账单原价 24.50 与此一致。系统改按袋宽阶梯（25cm=30、20cm=28）并写「忽略包名双」，七折后变成 21.00 或 19.60。

### 4.2 纸塑「双」仍封顶 16.5，且 ≥3 件袋费全免

标准高温纸塑在件数 ≥ 3 时直接返回件费，袋费（含双层第二只袋）默认不加（`chargeDoubleBagWhenCapped` 默认 false）：

```1834:1848:backend/src/main/java/com/hospital/backend/service/PricingEngine.java
        if (instrumentCount >= 3) {
            // ...
            String doubleNote = isDouble && bagFee2 > 0
                ? "（包名含\"双\"，但 ≥3 件袋费免收）"
                : "";
            notes.add("大于等于 3 件，按 " + fmt(perPackagePrice) + " 元/件 × " + instrumentCount
                    + " = " + fmt(packageFee) + " 元计费，不再计袋费。" + doubleNote);
            return packageFee;
        }
```

特色规则即使命中，后面仍有一段全局逻辑：纸塑、非低温、`skipPackaging=false` 时先加袋费，再在「双且件数 &lt; 3」时封顶 16.5（约第 581–594 行）。松北 Excel 明确取消了这个封顶。按第 2.1 节的客户补充：＜3 件的标准包材是材料列里每一只袋子的标准价之和（两只就收两只）；≥3 件只加宽度较大的那只外层，不加内层。代码按材料列书写顺序把第一段当外层，≥3 的加袋又优先取内层价，和外层定义相反。

### 4.3 「人工核对、已按原价暂计」之后价格仍被改写

特色规则 `manualReview=true` 时，引擎先把期望单价改成账单原价，并写入「已按账单原价 x 元暂计」（约第 313–320 行、第 852–856 行）。**这句写完之后** 第 581 行仍可能把袋费加到这个原价上，再封顶，再由编排器乘 0.7。`skipDiscount=true` 只挡住引擎内部的医院折扣，挡不住编排器第 84–114 行的内勤折扣。

关键词 `"/双"` 按斜杠分段时能命中 `/双/`（骨膜剥离子），命不中 `/双保/`（成人头钉）。Excel 是「包名称带双」，`双保` 应命中松北纸塑规则。类型是低温等离子时，种子 `acceptedTypes` 只有纸塑袋，落到 4.1 的低温分支，这是对的；错在低温分支把省二排除了。

## 5. 截图逐条

金额以截图为准。规则单价列是编排器折扣之后的数。

### 5.1 省二院松北，行 784，`Z镜头-1/双/Z2045`

- 科室妇科病房，类型额外包(低温等离子)，包数 1，器械数 1。
- 原单价 24.50，规则单价 21.00，差额 −3.50。
- 抽屉：低温纸塑袋(双) 25cm 阶梯 → 「忽略包名「双」追加袋费，单价 30」→ 「规则单价 30 与原账单 24.50 不一致」→ 七折 21.00。

原因：类型不是纸塑袋，松北纸塑「双」规则正确地没有命中。应走通用「低温 + 双 + 1 件 = 35，市二除外」。`isHrb2ndHospital` 把省二排除，改收 25cm 袋价 30，再七折。30 是七折前的中间价，气泡/抽屉拿它和 24.50 对比，列上已经是 21.00。24.50 = 35 × 0.7，和账单一致，说明账单按 35 元再折，系统少算了双层固定价。

### 5.2 省二院多材料，松北，行 59，`成人头钉-3/双保/Z7520`

- 手术室，额外包(纸塑袋)，器械数 3，包数 1。
- 原单价 13.30，规则单价 11.55，差额 −1.75。
- 抽屉规则名是「高温纸塑袋(双)10cm计费」，不是「省二松北双≥3…」。步骤写：≥3 件按 5.50×3=16.50，不再计袋费（包名含双但袋费免收），再七折 11.55。

原因：包名是 `/双保/`，关键词 `/双` 对不上「包名称带双」，特色规则未命中，掉进标准高温阶梯。标准阶梯 ≥3 件袋费全免。Excel 要求 5.5×3 再加外层纸塑袋，且这条是松北特色价，`skipDiscount=true`，不应再乘 0.7。11.55 = 16.50 × 0.7，是「全免袋费 + 多打一次七折」。

### 5.3 `骨膜剥离子（窄）-1/双/Z1026`

- 原单价 9.45，规则单价 11.55，差额 +2.10。
- 规则名已经是「省二松北双&lt;3按件5.5含包材 + 纸塑袋费」。
- 步骤 8：「需人工核对，已按账单原价 9.45 元暂计。」
- 随后仍叠加纸塑袋费，并出现 16.50 封顶，再七折得到 11.55。

原因：特色规则命中了（`/双/` 能对上），但 `manualReview` 先把价格改回 9.45 并写死这句话，后面的袋费、16.5 封顶、编排器七折继续改价。Excel 写明松北 **没有** 16.5 上限，且该规则 `skipDiscount=true`。步骤 8 与最终 11.55 矛盾，属于说明文本错误，不是客户看错。

### 5.4 `肾镜-1/双Z2075`

- 手术室，低温纸塑 20cm，原单价 24.50，规则单价 19.60，差额 −4.90。
- 抽屉：忽略双，单价 28，再七折 19.60。

原因与 5.1 相同。28 是 20cm 单件袋价，不是 35。19.60 = 28 × 0.7。账单 24.50 仍等于 35 × 0.7。包名是 `/双Z` 粘连，纸塑特色关键词更不容易命中；这条类型走低温，本来也不该用纸塑 5.5 规则。

### 5.5 件数气泡：`扩镜4.5号-1` 的「5」没有字段来源

省二院多材料 9 月，松北，行 64，妇科病房：

| 列 | 值 |
| --- | --- |
| 包名 | `扩镜4.5号-1/Z7526` |
| 包装材料 | 高温纸塑袋 `75*260` |
| 器械数 | 2 |
| 包数 | 2 |
| 原单价 / 规则单价 | 5.60 / 5.60，差额 0.00 |

账单自身是齐的：`-1` 表示单包 1 件，包数 2，1 × 2 = 2，与器械数 2 一致。单价也一致，计价规则是「高温纸塑袋 10cm」，没有价格冲突。这一行不该出字段核对失败。

感叹号气泡却是：

> 包名件数合计 5 × 包数 2 = 10 与器械数列 2 不一致

气泡里的 5 不是器械数、不是包数、不是单价，材料列 `75*260` 里也没有 5。它是解析器把两个不相干的数字加出来的。

`PackNameSpecParser.extractBasePieceCount` 对斜杠前的 `扩镜4.5号-1` 做两步：

1. 连字符件数 `[-－](\\d+)` 命中 `-1`，得到 1。这是唯一真正的件数。
2. 紧凑段 `汉字+整数`（`COMPACT_NAME_DIGIT_SEGMENTS`）再扫同一串，命中 `扩镜` + `4`。`4` 后面是小数点，不是件数。

两步相加：1 + 4 = **5**。校验器用这个 5 当「包名件数合计」，再乘包数 2，得到 10，和器械数 2 比较，于是写入 `INSTRUMENT_COUNT_MISMATCH`。气泡只原文拼接这条 violation（`validationIndicatorMessages`），所以价格旁边出现一句和价格无关、数字也对不上任何列的话。

代码里本来有一条排除：紧凑段数字后面如果紧挨着 `号`、`度`、`°`，这段不算件数（`isValidCompactCountSegment`，约第 302–306 行）。单测 `DMD光源2号-1` 能得到 1，就是因为 `2` 后面直接是 `号`。`4.5号` 的 `4` 后面是 `.`，排除条件看不到后面的 `号`，`4` 被当成件数。`.5` 被丢掉，既不进件数，也不保留成规格。

同一张图里另外三行是同一个漏洞，只是包数是 1，看起来更像「凭空多出来的件数」：

| 行 | 包名 | 误加出来的件数 | 气泡会写成 | 实际应核对 |
| --- | --- | --- | --- | --- |
| 65 | `扩镜5.5号-1/Z7526` | 5 + 1 = 6 | 6 × 包数 1 = 6，器械数 1 | 1 × 1 = 1 |
| 66 | `扩镜7.5号-1/Z7526` | 7 + 1 = 8 | 8 × 1 = 8，器械数 1 | 1 × 1 = 1 |
| 83 | `扩棒3.5号-1/Z7526` | 3 + 1 = 4 | 4 × 1 = 4，器械数 1 | 1 × 1 = 1 |

这四行原价和规则价都是 5.60。感叹号不是计价差异，是规格小数被截成整数后硬加进件数。`N.N号` 整段都应视为型号（扩镜号、扩棒号），只保留 `-1` / `-1件` 作为单包件数。

### 5.6 `卵泡仪270*2.5（双层）`，包数 3，器械数 1，原价 7.15，规则价 5.60

`PackNameSpecParser.extractMmSize` 用第一个 `数字*数字`。`270*2.5` 会截成 **270×2**（小数只吃到 `2`），再和包装材料 `75*340` 比较，打出：

> 包名尺寸 270*2 与包装材料尺寸 75*340 不一致

`270*2.5` 是倍率/规格，不是袋的毫米尺寸。气泡因此在价格旁边弹出一条和钱无关、而且数字是截断出来的尺寸矛盾。整行会被涂成字段核对底色。若包名解析再把 `270` 附近的数字加成件数，会再拼一条器械数矛盾。两条叠在同一个气泡里，读起来像计价说明，实际全是字段解析误报。

## 6. 颜色标记为什么不稳定

对账主表的行类名只有 `fieldConsistencyRowClass`（`reconciliation/index.vue` 约第 1579 行）。它在同时满足下面两点时加上 `field-consistency-row`（底色 `#fff7f7`）：

- `status !== 'unchanged'`
- 存在字段核对问题，或存在 error 级账单校验（空包材、器械数为 0、缺字段）

单价差额 **不会** 给主表加行底色。`detail-row-diff`（`#fef0f0`）只在任务详情弹窗 `ReconciliationJobDialogs.vue` 里使用，主对账表不用。

单元格颜色在 `fieldConsistencyCellTone`：

- 器械件数不一致：器械列、包名列是琥珀色。
- 袋尺寸、包材类别、空包材、缺字段：相关列是红色。
- 包名同时有件数问题和尺寸问题时，包名优先走琥珀色，尺寸红只落在包装材料列。同一行会红一块、黄一块。
- 高亮列只有类型、包名、包装材料、器械数。单价列只有感叹号，没有单元格底色。

因此客户会看到：

| 行的实际情况 | 整行淡红 | 单元格红/琥珀 | 感叹号 |
| --- | --- | --- | --- |
| 只有单价不一致（Z 镜头、成人头钉、肾镜） | 无 | 无 | 有 |
| 只有件数/尺寸误报，且单价一致（扩镜、部分 9 月行） | 有 | 有 | 有 |
| 内勤计价命中，字段其实不一致 | 无（引擎没跑，没有 violation） | 无 | 通常无 |
| 状态被标成 unchanged（无需修改） | 被清掉 | 被清掉 | 视单价是否仍不一致 |

斑马纹选择器没有 `!important`，字段行选择器有。字段行本身能盖住斑马纹。固定列使用 `background-color: inherit`，继承不到行类上的单元格背景时，左侧冻结列仍是白的，右侧滚动列是淡红，看起来像「同一行有的格子标了、有的没标」。

### 6.1 科室标签上的异常数消失

客户截图是「省医院香坊多材料9月.xlsx」：61 个工作表，总行 3875。科室标签（CCU、产科、手术室等）后面现在只剩一个灰色数字。顶部统计是「修正 433、待复核 0」。打开「仅异常」后，单价不一致仍有 433 行，但每个科室名称后面不再出现原来的异常数。

标签上其实有两个数，样式不同：

| 位置 | 样式 | 数据 | 显示条件 |
| --- | --- | --- | --- |
| 科室名后面的灰色数字 | `sheet-segment__meta` | 前端解析时该表的总行数 `sheet.dataRows` | 一直显示 |
| 再后面的琥珀色小标 | `sheet-segment__warn` | `savedSheetWarningCounts[科室名]` | 该数存在且大于 0 |

灰色数字不是异常数。客户说「原来科室后面还会显示每个科室有异常的数量」，指的是琥珀色小标。小标的模板在 `ReconciliationEntryStickyHeader.vue` 第 73–78 行：`v-if` 用的是 JavaScript 真值，0 和缺省都不渲染。

这个数的来源只有一种状态。保存时 `computeSheetStats`、详情接口 `buildJobResponse` 都只在 `row.status` 等于 `"warning"` 时给该 `sheetName` 加 1。`corrected`（修正）、`unchanged`、字段核对、单价不一致都不进这个 map。前端「仅异常」的口径宽得多，包含待复核、已修正、单价不一致、人工审核、字段核对、金额差额（`reconciliationAnomaly.ts`）。所以筛选里能看到 433 条单价不一致，科室标签上仍然是空的。

这 433 行为什么不是 `warning`：引擎本来把有差额、字段不一致、需人工核对的行标成 `warning`（`PricingEngine` 约第 645 行的注释：有差额先待复核，用户点「一键修正」后才变成 corrected）。内勤折扣命中并改写单价后，`ReconciliationPricingOrchestrator.syncCorrectionTotals`（第 276–288 行）按总价差额把状态覆盖成：

- 差额不为 0 → `corrected`
- 差额为 0 → `unchanged`

覆盖时不保留原来的 `warning`，也不看字段核对。香坊院区有账单折扣，大量行会走进这个分支。整单统计就变成「修正 433、待复核 0」，`sheetWarningCounts` 全是 0 或空，琥珀色小标全部不渲染。折扣把单价刚好折回原价的行还会变成 `unchanged`，连第 6 节的行底色也会被清掉。

「一键修正」和全量 `reprice` 走 `applyBatchCorrection`（约第 2589 行），同样只按差额写成 `corrected` 或 `unchanged`，效果相同。

科室名本身对得上：多工作表文件里，行的 `sheetName` 就是 Excel 表名（`ExcelBillImportSupport` 第 112 行，非合并表时用 `sheetName`），标签用的也是工作表名。这次不是名字对不上，是异常数被状态覆盖写成了 0。

客户要求把每个科室的问题高亮留下来。状态已经是「修正」的行，仍然是这个科室的问题记录，必须计入该科室的琥珀色数字，不能因为状态从待复核改成了修正，科室标签上的问题数和高亮就消失。

因此科室计数至少要包含：

- `warning`（待复核）
- `corrected`（修正）

只统计待复核时，香坊这种「修正 433、待复核 0」的账单每个科室都会是空白。把修正行按 `sheetName` 加进 `sheetWarningCounts`（或单独的问题数）之后，科室标签才能继续标出该科室还有多少问题行。行上的问题高亮同样不能因为状态变成修正就被清掉。

## 7. 感叹号气泡：该改的说明

显示条件 `shouldShowValidationIndicator`：字段问题、error 级校验、规则单价 ≠ 原单价、规则名是「未命中规则」或含「未识别包装类型」，都会出 `!`。

气泡正文 `validationIndicatorMessages` **只收集** 字段核对 violation 和 error 级账单校验。计价备注（忽略双、袋费免收、暂按原价、七折、规则单价与原账单不一致）不进气泡。

`ReconciliationDataTable.vue` 约第 442 行：没有上述消息时，退回文案：

> 字段核对未通过，请核对原始账单（仍展示系统计价结果）

这条文案在「仅仅是单价不一致」时是错的。字段可能完全一致，价格是双层规则或折扣造成的差额。用户会以为原始账单字段坏了。

字段消息本身也有三类错：

1. **规格小数被截断后加进件数。** `扩镜4.5号-1` 的气泡「5 × 包数 2 = 10」里，5 不是任何一列。`-1` 是件数 1，`4.5号` 里的 `4` 因为后面是小数点、排除规则只看紧挨着的 `号`，被加进件数。正确核对是 1 × 包数 2 = 器械数 2，本行不应出感叹号。详见第 5.5 节。`270*2.5` 被截成袋尺寸 `270*2` 是同一类截断。
2. **抽屉步骤与气泡、与规则单价列互相打架。** 「已按原价 9.45 暂计」之后又加袋费和七折；「规则单价 30 与 24.50 不一致」里的 30 不是列上的 21.00。
3. **≥3 件「包名含双，但袋费免收」** 是标准阶梯的旧说明。松北 Excel 要求外层袋照收，这句话不能再出现在松北纸塑「双」上。

气泡应在计价全部结束后生成，至少分开三句，且每句使用最终规则单价：

- 字段不一致：保留现有字段句，但规格类数字不要计入件数和毫米尺寸。
- 单价不一致：写最终规则单价、原单价、差额，以及命中的那一层（内勤计价 / 特殊 / 标准 + 内勤折扣）。
- 人工核对：只有最终单价真的停在账单原价时才写「已按原价暂计」。后面如果又加了袋费或折扣，这句应删除或改成「规则要求人工核对，系统仍给出了试算价 x」。

## 8. 和「不能因为字段不一致就停止计价」的关系

引擎路径没有在字段失败时 `return`。`forceConsistencyWarning` 只把状态打成 `warning`，期望单价继续按规则算。这一点符合客户要求。

不符合要求的是另外三处：

1. 内勤计价命中时整段引擎被跳过，字段标记和特殊计价一起消失。若内勤价覆盖了特殊价，字段标记仍然应该留下。
2. `【字段核对】规则单价 … 不一致` 使用折扣前的中间价，读起来像计价被字段核对打断、停在了 30 或 9.45。
3. 气泡在没有字段 violation 时仍说「字段核对未通过」，把价格差额伪装成字段错误。

建议的落地顺序（供下一轮改代码，本次未改）：

1. 字段校验从引擎里拆到编排器最前，内勤计价命中与否都执行，只标记不返回。
2. 然后内勤计价；未命中再特殊计价；再内勤折扣。`skipDiscount=true` 的特色规则不再进入第 4 步。
3. 松北纸塑「双」按新 Excel 和第 2.1 节两条补充：先用宽度区分内外层（宽的是外层，不看书写顺序）。＜3 为 5.5×件数 + 材料列里全部袋子的标准价（两只就收两只），不封顶 16.5，材料列只有一只时不要把同一尺寸复制成第二只。≥3 为 5.5×件数 + 较宽那只外层的标准包材，不加内层。关键词改为包名包含「双」（`双保`、`双层`、`/双Z` 都算）。`manualReview` 若仍要保留，不能在写完「暂按原价」之后再加袋费和折扣。敷料包（所有医院）不做包材核对，规则单价保持睿思原价，不再打折。
4. `isHrb2ndHospital` 只匹配哈尔滨市第二医院 / 市二院，不匹配黑龙江省第二医院。低温单件「双」恢复 35 元后再折扣。
5. 主表：单价不一致与字段问题用可区分的标记。每个科室的问题高亮要保留：科室琥珀色数字必须把「修正」（`corrected`）和「待复核」（`warning`）都算进去，不能只统计待复核。状态变成修正后，该科室的问题数和行上的问题高亮仍然留下。
6. 气泡与抽屉步骤都改用最终单价重写。`N.N号`（如 `4.5号`、`5.5号`）整段视为型号，不把小数点前的整数加进件数；只认 `-N` / `-N件`。`270*2.5` 这类倍率不要进入 `N*M` 袋尺寸比对。
